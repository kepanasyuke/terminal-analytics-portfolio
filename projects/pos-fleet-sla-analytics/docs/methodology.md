# Методика расчётов

## Период наблюдения

Период задаётся выгрузкой (`period.csv`), а не диапазоном инцидентов. Устройство,
которое ни разу не сломалось, всё равно входит в знаменатель доступности — иначе
«тихие» устройства просто исчезают из расчёта и средняя доступность растёт.

## Доступность

```
доступность = 1 − суммарный простой устройства / период наблюдения
```

Правила:

1. Пересекающиеся инциденты схлопываются: начало каждого сдвигается до конца
   предыдущего простоя по этому устройству (`MAX(opened_at, предыдущий closed_at)`).
2. Открытые инциденты обрезаются концом периода наблюдения, а не текущим временем.
3. Устройства в статусе `DECOMMISSIONED` исключаются из средних по парку.
4. Средняя доступность — арифметическое среднее по устройствам. Альтернатива
   (взвешивание по часам) скрывает одиночные «мёртвые» киоски в общем фоне.

## Сроки и нарушения SLA

Для инцидента фиксируются два норматива из договора:

- **реакция** — не более 25 % норматива решения;
- **решение** — `sla_hours` по критичности (`p1_hours`, `p2_hours`, `p3_hours`).

Нарушением считается просрочка любого из двух. Просрочки считаются отдельно:
`response_overdue_h` и `resolution_overdue_h`, чтобы было видно, где рвётся процесс —
на приёме заявки или на выезде инженера.

## Неустойка

```
штраф_за_инцидент = месячная_плата × ставка_% / 100 × ceil(просрочка_решения_ч)
штраф_за_месяц    = min(сумма штрафов, месячная_плата × лимит_% / 100)
```

- просрочка округляется вверх до полного часа — так считает договор;
- лимит применяется на уровне «договор × месяц», а не к отдельному инциденту;
- просрочка реакции в штраф не входит: она влияет на показатель соблюдения SLA,
  но не на деньги. Это осознанное разделение, иначе один и тот же час штрафуется дважды.

В витринах `mart_penalty_month` лежат три суммы: начислено без лимита (`raw_penalty_kop`),
лимит (`penalty_cap_kop`) и к выставлению (`billed_penalty_kop`).

## Кандидаты на замену

Отбор не по одному показателю, а по совокупности:

| Приоритет | Условие |
| --- | --- |
| ВЫСОКИЙ | доступность < 90 % или 4+ инцидента P1 |
| СРЕДНИЙ | доступность < 95 %, 3+ P1 или 8+ инцидентов |
| НАБЛЮДАТЬ | 5+ инцидентов при нормальной доступности |

Причина указывается текстом: «хронические отказы, износ», «повторные критичные
инциденты», «выработан ресурс» (установлено раньше 01.06.2023). Это то, что
показывают партнёру на встрече, вместо сухой таблицы.

## MTTR

Среднее время решения по **закрытым** инцидентам. Открытые не входят: иначе MTTR
зависит от даты запуска отчёта и всегда занижен для свежих инцидентов.

## Проверка

Тест `test_sla_breach_count_matches_independent_calc` пересчитывает нарушения SLA
на чистом Python прямо из выгрузки и требует совпадения с витриной.
Тест `test_penalty_formula_matches_contract_terms` проверяет формулу штрафа по
договорным ставкам, `test_penalty_is_capped_per_contract` — применение лимита.
