# Методика расчётов

Документ объясняет, как считаются показатели и почему именно так. Все формулы
продублированы в SQL: `sql/03_reconciliation.sql`, `sql/04_control_totals.sql`,
`sql/05_marts.sql`.

## 1. Сверка двух систем

**Ключ сопоставления** — `rrn`. Это единственный идентификатор, который существует
в обеих системах и не меняется при передаче операции.

**Порядок шагов:**

1. Дедупликация каждой стороны по `ROW_NUMBER() OVER (PARTITION BY rrn)`.
   Полные дубликаты не выбрасываются бесследно: количество повторов фиксируется
   в `stg_acquiring_duplicates` и выходит в отчёт отдельным классом.
2. Полное внешнее соединение: `LEFT JOIN` терминал → процессинг плюс анти-выборка
   из процессинга (`WHERE NOT EXISTS`). Такой вариант переносим на PostgreSQL и MS SQL
   без `FULL OUTER JOIN`.
3. Классификация с приоритетом (первое совпавшее правило выигрывает):

| Приоритет | Класс | Условие | Что значит на практике |
| ---: | --- | --- | --- |
| 1 | `DUPLICATE_IN_ACQUIRING` | в процессинге более одной записи с одним RRN | двойное списание или повторная проводка |
| 2 | `MISSING_IN_ACQUIRING` | операция есть в журнале терминала, в процессинге нет | операция не дошла до хоста, деньги не списаны |
| 3 | `MISSING_IN_TERMINAL` | операция есть в процессинге, в журнале нет | «лишняя» проводка, риск претензии клиента |
| 4 | `AMOUNT_MISMATCH` | `terminal_amount_kop <> acquiring_amount_kop` | расхождение суммы в копейках |
| 5 | `STATUS_MISMATCH` | статусы не совпадают | клиенту отказано, а деньги списаны (или наоборот) |
| 6 | `TIMESTAMP_DRIFT` | разница во времени больше 10 минут | сдвиг часов терминала, риск при разборе претензий |

Порог 10 минут выбран так: в пределах этого окна расхождение объясняется задержкой
передачи и не мешает сопоставлению операции с расчётом. Порог вынесен в условие
одного `CASE` и меняется в одном месте.

**Сумма под риском** (`amount_at_risk_kop`) — не «разница сумм», а оценка денег,
которые могут быть потеряны:

- пропажа в процессинге — вся сумма операции;
- пропажа на терминале — вся сумма проводки;
- расхождение суммы — модуль разницы;
- расхождение статуса — сумма операции (риск чарджбэка);
- дубликат и сдвиг времени — 0, это операционные дефекты, а не прямые потери.

## 2. Контрольные суммы

Сверка итогов «партнёр × день» проверяет полноту выгрузки, а не корректность отдельных
строк. Инвариант, который держится всегда:

```
SUM(control_totals.cnt_diff)    = COUNT(процессинг) − COUNT(терминал)
SUM(control_totals.amount_diff_kop) = SUM(процессинг) − SUM(терминал)
```

Это проверяется тестом. Если инвариант сломался — потерялись строки при загрузке,
а не «разошлись данные».

## 3. Доступность устройства

```
доступность = 1 − суммарный простой / время наблюдения
```

Три решения, без которых показатель врёт:

1. **Пересекающиеся инциденты схлопываются.** Если два инцидента наложились по времени,
   простой считается один раз: начало каждого инцидента сдвигается до конца предыдущего
   (`MAX(opened_at, предыдущий closed_at)`). Без этого доступность уходит в минус.
2. **Открытые инциденты** обрезаются по концу периода наблюдения, а не по текущему времени:
   иначе показатель зависит от даты запуска отчёта.
3. **Выведенные из эксплуатации устройства** исключаются из средних по парку: они не
   обязаны быть доступны, но остаются в построчной таблице для истории.

Средняя доступность парка — `AVERAGE` по устройствам, а не по часам. Так одно проблемное
устройство не «растворяется» в общем фонде, а видно в топе худших.

## 4. MTTR и SLA

- **MTTR** — среднее время закрытия по закрытым инцидентам, в часах.
- **SLA** задан по критичности: P1 — 4 ч, P2 — 8 ч, P3 — 24 ч, P4 — 72 ч.
- **Нарушение SLA** — инцидент, у которого фактическое время закрытия больше нормы.
  Для незакрытых инцидентов используется время до конца периода — это консервативная
  оценка: реальное время закрытия будет не меньше.

## 5. Деньги

Суммы хранятся в копейках (`INTEGER`), рубли получаются делением на 100 только
на выводе. Причины:

- `0.1 + 0.2 ≠ 0.3` в плавающей точке — на миллионах операций копейки «набегают»;
- в Excel и Power BI пересчёт идёт по той же целочисленной сумме;
- сверка сумм сравнивает целые числа на равенство, без допуска.

Возвраты (`REFUND`) приходят отрицательными — при суммировании они автоматически
уменьшают оборот, отдельная логика не нужна.

## 6. Доля расхождений

```
доля расхождений = расхождения / операции
```

Считается к числу операций в журнале терминалов, а не к числу совпавших строк:
иначе показатель «улучшается» при росте пропаж в процессинге.

## 7. Проверка качества сверки

Генератор до построения источников фиксирует, какие RRN испорчены и как именно
(`data/raw/_injected_defects.json`). Тест `test_reconciliation_finds_exactly_injected_defects`
требует точного совпадения по каждому классу. Это превращает «сверка работает»
в измеримое утверждение: ложных срабатываний нет, пропусков нет.

Ожидаемое соответствие:

| Класс в отчёте | Что внесено в данные |
| --- | --- |
| `MISSING_IN_ACQUIRING` | удалено из процессинга + операции только с терминала |
| `MISSING_IN_TERMINAL` | удалено из журнала терминала + операции только в процессинге |
| `AMOUNT_MISMATCH` | сумма изменена на 1…500 копеек |
| `STATUS_MISMATCH` | статус перевёрнут (APPROVED ↔ DECLINED) |
| `TIMESTAMP_DRIFT` | время сдвинуто на 11…240 минут |
| `DUPLICATE_IN_ACQUIRING` | строка процессинга продублирована |

## 8. Обезличивание

При передаче данных заказчику применяются правила:

- PAN: остаются BIN (6 цифр) и последние 4 цифры;
- серийный номер: первые 2 и последние 4 символа;
- телефон и e-mail маскируются;
- RRN по умолчанию не трогаем (по нему сверка), при необходимости — псевдонимизация
  `SHA-256(соль + RRN)`: одинаковые операции получают одинаковый токен, соединения
  в отчёте не ломаются, восстановить исходный RRN без соли нельзя.
