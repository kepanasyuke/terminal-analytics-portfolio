# Аналитика терминальной сети — портфель проектов

Четыре самостоятельных учебных проекта о данных терминального парка: POS-терминалы,
киоски самообслуживания и банкоматы. Общая тема — превратить сырые выгрузки в понятные
цифры: сойтись с процессингом, посчитать соблюдение SLA, заметить аномалию до того,
как она станет простоем, и разобрать поток заявок поддержки.

## Происхождение проектов

Это важно проговорить прямо, потому что вопрос возникает первым.

- **Все четыре проекта написаны с нуля в ноябре 2026 года** специально под вакансию
  аналитика в команде поддержки терминального оборудования. Общего кода с другими
  моими работами у них нет.
- **Это не форк, не копия и не доработка** существующих pet-проектов из репозитория
  `fumiklea` (системная утилита на C, REST API на Python, Banking Fraud Analytics,
  Harvard Mark II Bug Catcher, Currency Converter). Там другие домены и другие задачи;
  те репозитории не изменялись.
- **Данные синтетические.** В каждом проекте есть генератор, который создаёт
  правдоподобный поток операций, инцидентов или заявок. Генератор также фиксирует
  эталон: какие строки специально испорчены, где заложена аномалия, какая категория
  у заявки на самом деле. Благодаря этому качество алгоритмов измеряется числом
  (полнота, точность), а не оценивается «на глаз».
- **Одинаковый порядок работы во всех проектах:** постановка и домен → генератор
  данных с эталоном → расчёты (SQL или Python) → отчёт → тесты на эталоне.
  Именно это, а не объём кода, показывает, как я подхожу к задачам.

Полная история коммитов по каждому проекту осталась в отдельных локальных репозиториях;
здесь проекты собраны вместе — по одному коммиту на проект.

## Структура

```
projects/
  pos-reconciliation-analytics/     src/ sql/ tests/ docs/ README.md
  pos-fleet-sla-analytics/          src/ sql/ tests/ docs/ README.md
  pos-transaction-anomaly-monitor/  src/ tests/ docs/ README.md
  servicedesk-ticket-analytics/     src/ tests/ docs/ README.md
```

Внутри каждого проекта:

| Папка | Что там |
| --- | --- |
| `src/` | генератор данных, расчёты, сборка отчёта, библиотека графиков |
| `sql/` | схема и витрины (в проектах, где расчёты идут на SQL) |
| `tests/` | проверки на эталоне: полнота, формулы, границы значений |
| `docs/` | методика: формулы, пороги, почему принято именно такое решение |
| `data/`, `reports/` | создаются при запуске, в git не попадают |

## Как запустить

Нужен Python 3.10+ (проверено на 3.14) и SQLite 3.39+. Внешних пакетов нет —
только стандартная библиотека: проекты запускаются на любой машине без установки
зависимостей и без интернета.

```powershell
cd projects/pos-reconciliation-analytics
python src/generate_data.py
python src/build_db.py
python src/run_sql.py
python src/report.py
```

```powershell
cd projects/pos-fleet-sla-analytics
python src/generate_fleet.py
python src/pipeline.py
python src/report.py
```

```powershell
cd projects/pos-transaction-anomaly-monitor
python src/generate_series.py
python src/detect.py
python src/report.py
```

```powershell
cd projects/servicedesk-ticket-analytics
python src/generate_tickets.py
python src/analyze.py
python src/report.py
```

Тесты любого проекта:

```powershell
cd projects/pos-fleet-sla-analytics
python -m unittest discover -s tests -v
```

Результат каждого запуска — `reports/dashboard.html` (самодостаточный файл, открывается
двойным щелчком) и `reports/summary.md`, плюс витрины в `data/processed/`.

## Графика в отчётах

Дашборды рисуют данные сами: линейные графики динамики, донаты структуры, столбцы
сравнений и анимированные счётчики KPI. Всё на инлайновом SVG без библиотек, CDN
и обращений к сети; анимация отключается системной настройкой `prefers-reduced-motion`.
Графики строятся из тех же витрин, что и таблицы, поэтому не расходятся с цифрами.

## Стек

Python (стандартная библиотека, `sqlite3`, `csv`, `unittest`), SQL (оконные функции,
CTE, полное внешнее соединение), SQLite, Power Query M, DAX, подготовка данных
для Excel и Power BI.

## Ограничения

- Данные синтетические: цифры в отчётах — свойства генератора, а не рынка.
- Это учебные проекты, а не промышленный код: нет CI, нет развёртывания,
  нет обработки потоковых данных в реальном времени.
- Каждый проект решает одну задачу; сквозного ETL-пайплайна между ними нет намеренно —
  так видно, какое решение к какой задаче относится.
